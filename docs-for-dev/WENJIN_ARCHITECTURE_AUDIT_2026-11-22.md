## 1. 结论与范围

**当前系统已有真实智能体运行机制和可用的主要学习链路，但没有完整实现最初架构，当前工作树也未达到可发布的工程质量。**

它已经超出单纯的聊天界面：存在模型选择工具并执行的循环、持久化会话与项目状态、证据驱动的学习判断、多角色调用、个人诊断参数训练、规划决策、课堂生成和媒体任务。与此同时，不能把这些分别等同于完整心理世界模型、经过校准的个人数字孪生或完整 RSI。

本次是审查，没有修改业务实现。进行了源代码和架构文档核对、核心后端测试、完整前端单元测试、构建前检查、部署预检，以及内存反例和隔离测试库的故障注入。未进行收费模型的全面在线调用、真实学生长期实验、Linux 生产发布和多人容量验收。

## 3. 已复现的问题

优先级定义：P1 表示阻止发布或影响核心记录/自动决策可信度；P2 表示需要在规模使用及下一轮架构推进前修复。这里不使用“页面存在”推断“功能已验收”。

### F1 / P1：课堂页面无法通过 TypeScript 编译

位置：`web/components/learning/Classroom.tsx:476–479`。

同一个 `MarkdownRenderer` 重复传入 `allowHtml`。运行 `npm run typecheck` 报：

```text
Classroom.tsx(479,21): error TS17001:
JSX elements cannot have multiple attributes with the same name.
```

影响：当前工作树不能通过正式构建的类型检查。开发服务器仍显示旧页面不代表当前源码可发布。

建议：合并成唯一且明确的 HTML 策略；重新跑契约、类型和生产构建，不只复跑局部课堂测试。

### F2 / P1：课堂答题与诊断证据不是一次原子提交

位置：`deeptutor/learning/classroom.py:532–606`，重点 `599–606`。

`answer()` 在课堂记录事务中，通过 `store.mutate()` 另行提交学习证据，然后才保存课堂答案。证据按固定 ID 去重；重试时界面结果却依据本次传入的选项重新计算。

本次使用现有测试夹具、临时目录和隔离测试 schema 注入保存故障，未修改真实学生数据：

1. 第一次提交错误选项，学习证据已提交。
2. 课堂 `put()` 抛出异常，课堂答案未保存。
3. 使用正确选项重试。
4. 结果：课堂显示 `correct=True`，诊断证据仍为 `incorrect`，证据数量为 1。

这不是重复计数，而是同一次任务的事实出现分歧。

建议：课堂答题、学习证据及事件使用同一工作单元；或建立持久化作答回执及可靠投递机制。重试必须返回已提交的同一作答结果。补充“提交中断→重试→刷新→诊断读取”的故障测试。

### F3 / P1：策略评估可把每个难度层都更差的候选策略晋升

位置：`deeptutor/learning/strategy_effects.py:68–98、170–188、226–235`。

当前仅检查双方是否存在相同“知识点/题型/能力”层，然后直接汇总命中数，没有控制各层样本比例。

本次构造内存数据，在 `episodes()` 边界注入，执行真实 `metrics()` 和晋升函数：

| 层 | 基线 | 候选 |
| --- | --- | --- |
| 简单任务 | 19/20 = 95% | 162/180 = 90% |
| 困难任务 | 18/180 = 10% | 1/20 = 5% |
| 直接合并 | 37/200 = 18.5% | 163/200 = 81.5% |

即时和延迟两组都采用上述构成，真实函数输出进入 `monitoring` 并启用候选。候选在每层都更差，却因任务组成较容易而晋升。

这是算法反例，**不是对真实学生效果的实验结论**。代码虽然写了“非因果”提示，但仍会据此自动更换策略，提示不能替代决策保护。

建议：使用固定权重的分层比较或配对评估，明确独立评价单位、时间窗口和最小有效样本；控制任务难度、顺序与重复试验影响。在此之前不应仅根据当前合并指标自动晋升。

### F4 / P2：RSI 约束哈希与回归门禁没有验证真实教学行为

位置：`deeptutor/learning/evolution.py:13–15、50–61`。

当前约束哈希来自固定标签字符串；`regression_check()` 检查模板名、是否含 `expected_answer`、是否含 `Wait`，以及哈希是否非空。

内存中将候选的错误反馈提示改成“在学生尝试前直接给出完整答案”，保持其他字段后，检查仍然返回 `passed=True`。随后恢复原模板。

现阶段模板是固定的 Python 定义，这不表示任意用户已经能在线改写硬约束；它证明该检查不足以承担原架构承诺的行为回归门禁。

建议：对实际约束清单及版本计算摘要，另行记录候选模板内容摘要；增加真实动作和工具轨迹的回归场景，包括提前泄答、无证据撤架、来源越界和证据篡改。模板文字校验可保留为第一层静态检查。

### F5 / P2：项目改名会改变训练数据资格

位置：`deeptutor/learning/diagnostic_datasets.py:30–40`。

是否模拟数据取决于项目名称是否含“验收”“模拟”“synthetic”“test fixture”。本次相同观察记录在内存夹具中，仅改项目名称，训练合格数就从 0 变为 1。

影响：模拟数据可能因改名进入训练；正常学生的“模拟练习”项目也可能被错误排除。快照自身不可变，不能弥补快照生成前的资格判断问题。

建议：在证据或项目创建时持久化不可被改名改变的来源类型、synthetic 标记、采集版本和来源链；迁移历史数据时保守标记并保留理由。

## 5. 已有实现中值得保留的工程基础

1. **持久化与范围隔离**：账户、项目、对话和证据已有 PG 迁移基础，资源映射、用户与工作区作用域存在，不能再称为纯本地 JSON 单机原型。
2. **任务恢复机制**：个人训练和媒体等任务有持久化状态、租约、重试和并发领取机制。`FOR UPDATE SKIP LOCKED` 等是实际实现，不只是方案。
3. **证据纪律**：辅助完成、独立表现、无来源或语义评分的记录有区分，撤销和诊断重算存在；这比只用聊天语气判断“掌握了”更可靠。
4. **个人训练的保守启用**：实际拟合经典 BKT 参数，要求至少 50 条合格记录、至少两个有效序列且每个不少于 10 次，包含正误；按序列前 80% 拟合、后 20% 验证，比较 log loss/Brier，数据不足或不合格不应替换原参数。
5. **规划边界**：LLM 决定保持或调整顺序，应用时校验版本和知识点集合，不直接修改历史证据。
6. **学习接续**：新会话从共享项目状态构造交接，不要求把所有旧对话逐字塞进上下文。
7. **课堂版本**：草稿、发布、内容摘要和版本隔离存在，编辑不会直接覆盖全部历史学习证据与媒体资源。
8. **执行保护**：代码中存在 sidecar / Linux bwrap 沙箱和普通用户 SYSTEM 隔离要求；应用级 subprocess 需要管理员显式启用，MCP/CLI 也有用户侧授权边界。不能笼统认定所有学生能直接执行宿主机命令。
9. **恢复工具**：已有数据库备份和隔离恢复校验脚本。部分辅助服务仍用 SQLite、媒体仍在文件系统，不能声称所有数据已统一到 PG，也不必为了统一而机械重写所有辅助存储。

这些基础值得继续完善，但 F2 说明“用了 PG、做了幂等”仍不代表跨资源事务已经正确。

## 6. 关键未完成项与工程验收标准

### 6.1 目标驱动的教学闭环

当前 `models.py:677` 的 `target_level` 是文本，`wenjin.py:10–15、42` 的证据要求主要按知识点类型固定。学生“知道定义”与“独立完成应用建模”需要的最终证据应不同，不能只影响聊天口吻。

下一步建立可版本化目标契约：目标程度、可观察成功标准、时间与资源约束、学生确认和修改来源。它应进入诊断解释、任务选择、撤架理由、复习和结课条件；修改目标不能伪造已掌握证据。

### 6.2 画像与长期记忆

已有事实、学生自报及项目状态；未形成原设计全部心理状态模型。优先增加证据支持的知识/能力/误概念与不确定性，把“没有数据”明确显示为未知。情感、动机或认知负荷若无可靠证据，只能作为暂定假设或学生自报。

跨项目能力复用需要知识点对齐和证据适用范围，不能仅凭名称相似就合并。

### 6.3 诊断与个人训练

当前参数按当前用户/工作区/项目范围存储，依据有效知识范围启用；这不是每个学生部署一套独立大模型，也没有跨用户混合训练。训练按钮产生的是 BKT 参数拟合和后续规划任务，不是 LLM 微调。

需补齐：F2、F5、真实数据规模分布、生成题目答案可靠性、参数不确定性与稳定性、长时间重试/回退恢复、训练结果对新表现的持续验证。语义评分被排除出参数训练是保守措施，也会减少可用数据，应在界面清楚说明不足原因。

### 6.4 RSI 与多 Agent

在修复 F3、F4 前，应把策略结果视为探索观察，不能宣传已证明“自主提高教学能力”。先完成可比较效果评价、实际约束清单和行为回归，再扩展候选策略空间。

数字孪生、技能库和派生 Agent 若推进，需要明确输入、预算、权限、独立评估、版本、终止和回退。没有这些，不应只通过增加角色名宣称架构完成。

### 6.5 多人运行与运维

需要补充按用户限制的生成并发、任务公平性、媒体磁盘限额、延迟与失败监控、完整 DB+文件恢复、连接池和容量测试。

源码中日历和任务看板分别创建 SSE，隐藏标签页并未关闭连接：`web/features/calendar/store/calendar-store.ts:84`、`web/lib/task-board-store.ts:64`。此前多标签页阻塞现象与此模式一致，但本次没有网络抓包证明它是唯一根因。需要在实际网关协议下做多标签页验收，考虑跨标签共享连接或隐藏页面释放连接。

本机预检通过不代表 Ubuntu/TTS/TLS 已部署完成，也不代表已经支持大量学生。部署文档本身也保留了实际服务器与 Linux 语音验收条件。

### 6.6 交互与可用性

本轮确认了功能和数据流，未重走所有页面的真实学生交互，不能宣布“全部好用”。进一步验收至少包括：

- 新学生注册→配置自己的模型→无上传资料创建学习→明确目标→大纲确认→开始陪学。
- 学到一半新建同项目对话→继续待答任务→帮助请求→独立测验→诊断回看来源。
- 数据不足训练→明确解释；数据足够训练→计划保持或更新→显示理由→撤销。
- 课堂生成中断→续生成→课件编辑发布→音频/视频→导出→通过陪学检验，不将看完课件记为独立掌握。
- 一次选错后重试、网络中断、过期页面、多标签页及跨账号访问；两名学生互不读到对方项目、证据和密钥。

诊断首页应优先回答“我现在会什么、证据够不够、下一步做什么、为什么调整”，训练指标和原始事件放详情。不要再通过不断增加并排卡片掩盖任务主线。

## 7. 建议修复顺序及退出条件

### 第一批：建立可发布基线

- 修复 F1，更新两份生成契约，修正已过期的品牌/语言断言和测试路由夹具，清理异步错误及超时。
- 按仓库规则修复 Ruff 和格式问题，接入可重建的 PG 测试环境。
- 退出条件：契约、类型、生产构建、边界检查、规定测试和 CI 全绿；结果对应一个可复现提交。

### 第二批：保护事实与自动决策

- 修复 F2 的原子性和重试一致性；增加数据库故障与进程中断测试。
- 修复 F3 的分层评估；未通过前约束自动晋升。
- 修复 F4 的行为回归与约束版本、F5 的数据来源标记。
- 退出条件：本文反例均转为有意义的回归测试，现有学生记录可核对且不伪造补齐。

### 第三批：完成目标与学习连续性

- 目标契约驱动任务和达标标准；结构化画像区分事实、估计、学生自报和未知。
- 验证跨会话、延迟/迁移测验、逐步撤架和恢复支持，继续打磨诊断表达。
- 退出条件：用普通学生自己的模型配置完成上述真实流程，所有改变可追溯、可撤销或有明确不可逆说明。

### 第四批：多人生产验收

- Linux 真实部署、语音与视频提供方、TLS、任务隔离/公平性、容量、备份与文件恢复演练。
- 退出条件：先约定并测出并发与响应目标，记录故障、恢复时间和数据完整性，而不是凭测试数据行数推算学生容量。

### 第五批：继续扩展原始愿景

- 根据产品范围决定教师侧、跨项目迁移、技能库、校准孪生和更完整 RSI。
- 新 PBL 方案中的任务产物版本、里程碑、评价和双重能力证据另行设计验收，不能把已有课堂页面算作 PBL 引擎。
