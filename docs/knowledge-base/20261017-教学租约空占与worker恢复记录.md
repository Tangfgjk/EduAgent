# 教学维护异常导致空占租约

## 现象

运行持续停留 queued，下一次 worker 轮询也不能推进。注入一次维护异常可在 2 秒内稳定复现，不需要真实模型。

## 定位过程

`tests/test_worker_recovery.py::test_housekeeping_failure_does_not_strand_a_claimed_teaching_job` 走真实账号、HTTP 接受输入、Outbox 与 Worker。第一次 step 在维护处注入一次异常，随后恢复正常，第二次 step 应进入 awaiting_input。修复前连续两次实际运行均失败：`queued != awaiting_input`。

比较三条路径：领取后维护失败使租约空占；嵌入式 worker 未捕获周期异常会退出；普通教学执行失败则应走 pending 退避。最小复现直接区分了前两种风险与正常退避。

## 根因

`Worker.step` 原本先 `outbox.claim()` 再执行事务外的 `reap()`。若后者异常，已领取且未处理的任务保持 leased，直到默认 60 秒租约到期才能恢复。生产 CLI 有外层捕获，浏览器验收服务的线程则没有相同保护，存在周期异常退出后无人继续处理的风险。

这是通过故障注入确认的缺陷。此前 Edge 单次超时没有保留足够服务端日志，尚不能将其直接归因于本缺陷，见 inbox 的独立待验证记录。

## 解决方案

- 将维护步骤移到领取之前；维护失败不占据待处理任务。
- CLI 与嵌入服务共用 `run_loop`，周期异常后继续轮询，连续异常仅记录一次 unavailable，恢复记录 recovered。
- 教学任务记录内部 job ID、尝试次数和耗时，不记录租约 token、学生文本、SQL、连接地址或原始异常。
- 学生页区分等待、处理中、退避、等待恢复及暂停；不在等待时重复提交。

## 验证方法

```powershell
$env:RSI_TEST_POSTGRES='1'
.venv/Scripts/python.exe -m pytest tests/test_worker_recovery.py -q -p no:cacheprovider --basetemp .local/pytest-worker-recovery-check
```

最小用例已由失败转为通过；另有监督循环用例验证注入异常后仍完成同一任务，并断言日志不包含注入的秘密字符串。保持既有 fencing、重试退避、5 次上限与模型无自动重试规则。
