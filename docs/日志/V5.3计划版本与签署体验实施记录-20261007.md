# V5.3 计划版本与签署体验实施记录

更新时间：2026-10-07（Asia/Shanghai）  
版本标记：V5.3 / 计划模块第五阶段  
状态：本地实现与定向验证完成  
前置版本：V5.2 计划执行系统  
范围：补齐计划版本链、学习者签署边界与学生端版本决策界面；不把系统建议、任务执行或教师意见伪装成学生决定。

## 1. 设计原则

本阶段固定以下权责边界：

- 系统只创建 `proposed` 建议，不能直接启用或签署计划。
- 学生采纳建议后得到独立的 `draft` 草案；原系统建议留在历史中，不会被就地改写。
- 学生对草案或已签署计划进行调整时，服务端总是创建新 `draft` 和版本 Diff，绝不覆盖旧内容。
- `confirmed` 版本不可编辑；其后发起调整时，它继续作为当前有效计划，直到学生签署新的草案。
- 学生可以拒绝建议或草案；拒绝必须填写原因，原因仅作为后续建议参考，不用于能力、态度或任何评价。

统一状态如下：

| 状态 | 含义 | 是否可直接编辑／签署 |
|---|---|---|
| `proposed` | 系统建议，等待学生决定 | 可采纳为草案或拒绝，不可签署 |
| `draft` | 学生正在审阅或调整的草案 | 可继续形成新草案、拒绝或签署 |
| `confirmed` | 学生已签署、当前生效 | 锁定；只能据此创建下一版草案 |
| `rejected` | 学生已拒绝 | 保留原因与历史，不可继续操作 |
| `superseded` | 已被新草案或新签署版本替代 | 只读历史 |

## 2. 已完成的版本链

### 2.1 建议、采纳与草案分离

新增 `POST /api/path/propose`：路径推荐先保存为 `proposed`，学生可以在界面中审阅或拒绝。

学生使用“采纳为我的草案”后：

1. 原 `proposed` 版本标记为 `superseded`，保留其推荐内容、Diff 和审计记录；
2. 服务端创建一个新的 `draft`，内容相同但属于学习者的可编辑草案；
3. 路径节点对应的执行任务被物化为项目任务；
4. 新草案尚未生效，不能覆盖已有 `confirmed` 计划。

这使“系统推荐了什么”与“学生最终选择了什么”在版本历史中可区分、可追溯。

### 2.2 已签署版本锁定与下一版调整

`PlanService.modify` 现在支持两种合法入口：

- 调整 `draft`：旧草案成为 `superseded`，生成新草案；
- 调整 `confirmed`：已签署计划保持 `confirmed`，生成以它为基线的新草案。

后一种情形中，新草案的 `prior_version_id` 指向已签署版本，Diff 以其内容计算。只有新草案被学生签署后，旧 `confirmed` 才被标记为 `superseded`。因此不存在“保存调整时悄悄替换当前计划”的窗口。

### 2.3 任务、截止日期与里程碑的版本化应用

计划内容可以携带 `project_plan` 快照以及 `deadline_at`：

- 在项目编辑区修改任务、任务截止日期或里程碑时，如果项目已经建立目标契约，页面不直接改写项目；而是创建未签署计划草案。
- 保存学习节奏、计划截止日期和调整说明同样会创建新草案。
- 签署时服务端先验证项目快照，再把该安排应用到项目，并把计划截止日期写入项目目标契约。
- 应用安排时保留草案审阅期间已产生的任务完成状态、证据引用和系统新增的复习任务；草案不能擦除真实学习证据。

首次创建项目（尚无目标契约）仍可直接保存项目资料；建立目标后，后续计划性安排改动进入版本链。

## 3. 前端重新整理

计划页的“计划提案与签署”区已重排为一个清晰的决策工作区：

```text
查看版本 / 生成系统建议
        ↓
系统建议 ── 采纳为我的草案
        ↓
我的调整：节奏、计划截止日期、调整原因
        ↓
保存为新草案 ── 签署并启用草案
        ↓
拒绝原因（仅供后续建议参考）
        ↓
版本差异 + 版本时间线
```

具体改动：

- 顶部状态标签直接说明当前选中版本是系统建议、我的草案、已签署版本、拒绝版本还是历史版本；
- 系统建议和“我的调整”并列呈现，减少“建议”和“已生效计划”混在一起的误解；
- 拒绝原因单独呈现，并明确不会用于评价；
- 版本 Diff 优先展示节奏、截止日期、任务／里程碑数量变化和路径变化，完整 JSON 收入折叠区；
- 版本时间线可回看所有建议、草案、签署、拒绝和替代版本；
- 项目编辑区在有目标契约后会提示并自动走“保存为未签署草案”的路径，而不是静默覆盖当前已签署计划；
- 对桌面和窄屏补充了两栏／单栏响应式布局。

## 4. 服务端接口与数据边界

涉及的主要实现：

- `platform/app/learning/plans.py`
  - 采纳建议时保留原建议并生成新草案；
  - 已签署版本只能作为新草案的基线，不能原地修改；
  - 拒绝理由不能为空。
- `platform/app/gateway/routes.py`
  - `POST /api/path/propose` 保存系统建议；
  - 签署接口校验并应用已签署草案中的项目安排和截止日期；
  - 初始草案保留项目安排快照。
- `platform/app/gateway/learning_routes.py`
  - 计划工作区返回完整 `history`；
  - 采纳建议接口要求当前项目并创建执行任务。
- `platform/app/learning/workspace.py`
  - 生成项目安排快照、签署前验证、签署后合并应用；
  - 保留自动完成状态、证据与审阅期间新增系统任务。
- `platform/web/learning.html`、`platform/web/workbench/workbench.js`、`platform/web/workbench/workbench.css`
  - 新版决策工作区、Diff、时间线、拒绝理由与响应式布局。
