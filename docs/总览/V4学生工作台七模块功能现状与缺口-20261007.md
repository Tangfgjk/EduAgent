# 桂子问津 V4：学生工作台七模块功能现状与缺口

更新时间：2026-10-07（Asia/Shanghai）  
审查基线：V4 代码 `f62a3eb`、当前本地部署及随附演示数据  
文档性质：功能现状评估；不是新需求批准、真人试点许可或教育效果报告。

## 1. 目标与判断口径

项目的总目标是构建陪伴学生和教师的教育智能体，帮助学习者完成“目标设置 → 学习执行 → 反思归纳 → 迭代调整”的自我调节学习闭环。真正要观察的是**无辅助表现提升、认知层级变化和自主性增长**，而不是页面数量、答题量或模型生成量。目标依据见[总体架构设计](../架构/01-总体架构设计-20260916.md)和[最终功能清单](../进度/项目最终功能清单与一周实施计划-20261005.md)。

本报告区分三个层次：

| 层次 | 含义 | 当前判断 |
|---|---|---|
| 本地研究 MVP | 功能可在本地、演示课程和演示学习者上运行，证据与权限边界明确 | 主要功能已具备 |
| 真人试点 | 有教师审核课程、研究与监护授权、真实身份、测量方案及受控数据采集 | 尚未准入 |
| 长期伴生／生产平台 | 多项目长期协同、可靠教育效果、学校身份与运维体系 | 尚未完成 |

以下“已实现”指代码和本地操作路径存在，不等于真实教学效果已被证实。历史[V4 最终验收记录](../测试/V4最终集成验收与发布记录-20261006.md)记载 824 项测试通过；本次审查没有在新部署环境重跑全量测试，只做了代码、文档、编译／脚本检查及关键只读接口核对。当前仅启动学生主服务 `127.0.0.1:8000`；独立的仿真实验室和学校实例不在本次运行验收范围内。

## 2. 总体框架：项目如何组织

### 设计职责

理想情况下，“学习项目”应是贯穿各模块的主线：一个项目包含学生目标、有效计划、当前任务、陪学会话、到期复习、成长证据和讨论记录。学生进入某个项目后，应能看到“为什么学、今天做什么、学到了什么、接下来如何调整”。跨项目的成长总览则汇总长期变化。

### 目前已有

- 代码按职责拆为 `gateway`（接口与页面入口）、`learning`（课程、计划、证据、状态、复习等）、`orchestration`（会话与策略）、`core`（动作及硬规则）、`agents`／`llm`（候选建议与模型接入）、`governance`、`storage`、`operations`、`simulation`、`school` 等目录；学生页面由 [`platform/web/learning.html`](../../platform/web/learning.html) 和 `platform/web/workbench/` 承载。
- 学生工作台有六个顶部视图：**陪学、计划、复习、成长证据、设置、圆桌与探究**。左栏展示项目、目标、计划摘要和复习数量；教师、家长、研究入口独立放置。
- 可新建、修改、归档学习项目，为项目添加待办／进行中／完成任务，并记录关联的作答证据、会话和知识来源。项目保存使用版本号与并发检查，引用不能随意指向无权访问的材料。
- 项目与计划的数据模型已有衔接空间，主界面也能显示项目进度；移动端六标签布局已有适配。

### 尚未完成／需要澄清

- **项目尚未成为贯穿六个模块的真实上下文。** 当前项目切换在 [`presentation.js`](../../platform/web/workbench/presentation.js) 中主要打开“计划”页的项目编辑器；陪学选题、复习队列、成长图和圆桌请求仍以学习者或知识点为主要范围，没有随“当前项目”统一切换。页面上的“项目内”标识因此不能理解为所有数据已按项目隔离。
- 项目任务状态和实际学习事件之间主要靠手工管理或引用关联；尚无“完成一项陪学任务 → 自动反映到项目 → 触发下一步计划／复习”的完整产品流程。
- 顶层目标、项目、计划版本、知识点与会话的关系在界面上仍分散，学生难以一眼理解一段学习旅程的因果链。
- 目前只有本地单实例职责分离；学校多租户、正式身份和跨设备生产运行不属于已完成范围。

### 完成判据

选择项目 A 后，各页能一致显示 A 的目标、任务、相关陪学记录、复习和证据；切换项目 B 不会混入 A 的项目视图；跨项目成长总览另有明确入口。完成任务与证据、计划调整之间有可追溯的自动或人工确认关系。

## 3. 陪学

### 设计职责

陪学不是直接给答案，而是先了解学生状态、安排合适任务，让学生先尝试，在需要时提供逐级支架，并把作答与帮助情况记录为可信证据。

### 目前已有

- 学生授权教学用途后，可选知识点与版本化课程题目，启动初诊；题目不足或诊断预算耗尽会明确返回“缺资产／未知”，而非随机编造结果。
- 正式提交前由服务器发题并提供版本、内容哈希、有效期与提交凭据；重复提交、错误版本及并发冲突有约束。
- 练习题支持请求提示、作答、自评“独立／猜测／不会／跳过”、验证反馈；提示与辅助信息会进入证据。前测、后测、迁移测和延迟测不开放提示，防止测量混入受助答案。
- 可开启陪学会话、对话、提交会话题目作答，并按会话编号恢复。会话策略、验证器和硬规则共同约束动作；例如考试模式和提前给完整答案受到限制。
- 解释类作品可以提交为“待评审”证据，再由独立教师端追加 Rubric 评审；AI 不代签教师结论。

实现入口见 [`workbench.js`](../../platform/web/workbench/workbench.js)、[`learning_routes.py`](../../platform/app/gateway/learning_routes.py)、[`rules.py`](../../platform/app/core/rules.py)和[`service.py`](../../platform/app/learning/service.py)。

### 尚未完成／限制

- 当前课程资产仍为演示／合成来源，170 道评测题均标为 `demo` 校准状态；不能视为已通过教师逐题审核的正式课程。
- 教学策略、难度调整及支架渐撤虽有代码规则，尚无真实学生对照数据证明它们改善了独立表现。
- 开放式解释依赖教师评审闭环；程序验证器中的代码执行能力声明为“可信本地代码测试器”，不是可接收不可信学生代码的安全沙箱，也不是当前学生页的公开代码评测能力。
- 陪学任务尚未随当前项目自动组织；当前更接近“选知识点／题目学习”，而不是“沿项目目标连续推进”。

### 完成判据

采用教师审核、来源授权和冻结版本的课程，在明确的项目／计划上下文中派题；真实授权样本显示学生逐步减少提示依赖，且独立后测与迁移测改善。开放作答与安全边界按试点方案单独验收。

## 4. 计划

### 设计职责

计划应把学生自己的目标转成可执行路径，同时保留学生对节奏和最终计划的决定权；学习结果应持续反馈到下一版计划。

### 目前已有

- 学生可填写学习目标，系统根据知识点与已有状态提出学习路径建议，并说明“初诊、补练、复习、进阶”等节点的依据。
- 路径只是建议；学生可采纳为草案、修改节奏和说明、拒绝，只有本人签署后才成为有效计划。保存的计划有版本与状态，修改时显示变更。
- “学习项目”可登记项目说明、任务状态，并引用相关证据、会话和知识来源；项目修改有 revision／CAS 防止旧页面覆盖新版本。

实现见 [`plans.py`](../../platform/app/learning/plans.py)、[`workspace.py`](../../platform/app/learning/workspace.py)及学生页“计划”区域。

### 尚未完成／限制

- 有路径和草案，但缺少面向日、周的持续执行编排，例如明确的每日任务队列、偏离计划后的提醒与重排、完成情况自动回写。
- “路径建议 → 项目任务 → 陪学实际作答 → 复习 → 下一版计划”尚未形成连贯的自动反馈链；学生需要在多个页面手工对照。
- 当前目标和路径主要围绕知识点及演示题库，尚未验证真实课程的先修关系、学习负荷与教师干预流程。

### 完成判据

学生能从目标直接看到本周／今日可执行任务；任务与项目、知识点、陪学证据及复习明确关联；完成、延期或证据不足时，系统提出有依据的新建议，再由学生确认生效。

## 5. 复习

### 设计职责

复习应在适当时间要求学生**独立回忆**，而非重复看答案；结果用于修正保持度估计，并反馈给计划和成长记录。

### 目前已有

- 系统按知识点掌握与保持状态生成到期复习队列，显示到期时间和估计遗忘风险。
- 点击到期任务可进入相应延迟测验；复习提交带任务身份，不提供提示，形成独立复习证据。
- 复习与掌握状态基于有效证据更新；更正或撤回后可重建，不把无效证据继续用于状态判断。

实现见 [`review_port.py`](../../platform/app/learning/review_port.py)、[`service.py`](../../platform/app/learning/service.py)及 [`workbench.js`](../../platform/web/workbench/workbench.js)。

### 尚未完成／限制

- 保持度模型为 `retention-default-v1` 一类默认参数，尚未通过真实延迟作答校准；页面上的遗忘风险是模型估计，不是真实测量值。
- 当前主要是“打开队列后查看”，不是持续提醒、可调整复习节奏和跨设备通知的完整复习产品。
- 复习按知识点组织，尚未与项目任务、阶段目标及计划重排形成统一视图；课程若缺少匹配延迟题，页面会提示缺资产。

### 完成判据

真实、独立、延迟的作答数据足以校准保持度；到期任务有可用题目，复习结果能准确影响项目进度与下一版计划，并可验证长期保持改善。

## 6. 成长证据

### 设计职责

成长证据应回答“学生是否越来越能独立理解、迁移和完成任务”，同时允许学生追溯每个结论的来源，避免把模型估计当能力标签。

### 目前已有

- 展示四类基于当前有效证据的图：掌握度重放轨迹、首次独立作答累计表现、累计辅助比例、各知识点掌握估计；保持状态另以文字说明。
- 可查看 Evidence 明细、掌握与保持状态，以及前测→后测、前测→迁移测、前测→延迟测的可比性检查。
- 提供认知／自主性发展指标和来源相连的学习记忆；数据撤回或教师纠正后按有效证据重算，不用随机演示分数填充空图。
- 教师纠正保留原记录和替代关系；学生可从“设置”提出申诉，避免直接抹去历史。

实现见 [`presentation.js`](../../platform/web/workbench/presentation.js)、[`metrics.py`](../../platform/app/learning/metrics.py)、[`memory.py`](../../platform/app/learning/memory.py)。

### 尚未完成／限制

- 当前本地库只有 2 条有效学习证据；可比测量中前测 1 条、后测 0 条，接口明确返回 `insufficient_data`。因此没有证据证明无辅助表现提升，也不能由曲线推出教育效果。
- BKT 掌握值和保持值是模型估计；图中“轨迹”是对当前有效证据的重放，不是当时逐日冻结的历史能力档案。
- 真正的认知层级迁移、自主性变化与项目成果仍需要测量协议、足够样本、真实课程及独立评审；目前的指标只适合描述和研究准备。

### 完成判据

有同难度、同 Rubric、可追溯的独立前后测及迁移／延迟测；达到预设样本门槛，并明确区分个人描述性变化与群体教育效果。学生能从任一图表追到原始作答、题目版本和帮助记录。

## 7. 设置

### 设计职责

设置应让学生控制界面、教学用途授权和共享范围，并提供纠错与申诉通道；这种控制不能绕过教育安全规则。

### 目前已有

- 可调整紧凑布局、右侧学习上下文、高对比度和字号；这些设置仅改变展示，不更改教学规则。
- 学生可明确授予或撤回教学用途。撤回后前端清空学习视图，后端拒绝继续读取相关学习状态与证据；研究和自动进化用途默认不随教学授权开启。
- 可选择不共享／向教师／向家长／向双方共享摘要；教师和家长使用独立入口，家长摘要不包含原始作答证据。
- 学生可针对证据提交复核理由，形成待处理申诉，而不是直接删除或改写作答。

实现见 [`learning.html`](../../platform/web/learning.html)、[`presentation.js`](../../platform/web/workbench/presentation.js)、[`governance/service.py`](../../platform/app/governance/service.py)。

### 尚未完成／限制

- 字号、对比度和布局目前由页面脚本即时修改，未见持久化保存；刷新或换设备后不能保证保留偏好。
- 本地身份模块是可选的；当前部署未开启登录保护，只绑定本机回环地址，不能作为多人或公网服务。
- 当前共享与删除能力不等于正式监护关系核验、学校 RBAC／SSO 或跨备份／外部 Provider 的全面删除合规。

### 完成判据

偏好可按学习者安全保存；正式身份与监护关系经过核验；授权、撤回、共享和申诉在学生、教师、家长及备份／外部系统间有一致、可审计的执行结果。

## 8. 圆桌与讨论（界面名“圆桌与探究”）

### 设计职责

这一模块应帮助学生查证来源、听见不同观点、解释自己的思路，并通过“教给别人”发现理解漏洞。所有生成内容都应是可质疑的候选，而非自动决定。

### 目前已有

- 可按问题和知识点检索本地知识来源，显示来源、版本、片段与引用；来源导入由独立研究入口操作，限制文件根目录与身份重绑。
- 可查看当前知识点的候选策略卡；基于至少一条有效证据请求“提示者、怀疑者、评审者”单角色建议，或生成三角色圆桌报告。
- 可写一段自己的讲解交给“虚拟学生”，取得模拟误区提示。角色调用有预算和时限；候选报告不会直接修改掌握状态、签署计划或执行动作。
- 当前默认离线固定模板模式能演示边界；代码存在受控外部 Provider 接口和候选来源记录。

实现见 [`external_routes.py`](../../platform/app/gateway/external_routes.py)、[`derived.py`](../../platform/app/agents/derived.py)、[`retrieval.py`](../../platform/app/learning/retrieval.py)。

### 尚未完成／限制

- 本地 Provider 状态为 `external_model_smoke=not_executed`、`deterministic_demo`；真实模型的内容质量、失败回退、成本和安全性尚未经本次部署验证。
- “三角色圆桌”目前是候选报告的并列呈现，**没有经过验证的共识裁决**；也不是学生与真人教师／同伴的实时讨论空间。
- 当前检索为 BM25 与哈希词法特征，不是已验证的神经语义检索；引用可追溯并不等于来源内容必然正确。
- 圆桌结果尚未成为项目内可追踪的“讨论 → 学生选择 → 实践 → 验证”闭环；不能把建议自动晋升为教学策略。

### 完成判据

讨论围绕具体项目任务和作品展开；建议能引用可信来源、展示分歧与不确定性，并由学生或教师决定是否采纳；采纳后的行动与后续证据可追溯。真实 Provider 和真人协作另行通过安全、成本与教学质量验收。

## 9. 综合判断与优先顺序

这七个模块已提供“授权 → 目标／计划 → 陪学作答 → 复习 → 查看证据 → 反思讨论”的**本地可操作路径**，但当前最重要的缺口有两类：

1. **产品闭环缺口：**以项目为中心的上下文没有贯穿六个页面；计划、陪学、复习、证据和圆桌之间仍需较多手工跳转、手工引用与解释。
2. **证据准入缺口：**课程未完成真实教师审核，当前数据量不足，模型参数未由真人校准，外部 Provider 未验收，因此不能宣称教育效果或真人试点就绪。

建议的推进顺序：先定义统一的项目上下文及跨模块事件链；再用教师审核课程完成端到端的封闭样例；随后落实研究授权、身份和测量协议，采集足够的独立前后测／迁移／延迟证据；最后才讨论真人试点结论与学校生产化。具体外部门槛见[V4 收口计划](../进度/V4最终研究MVP收口开发计划-20261006.md)及[V4 覆盖与限制矩阵](../测试/V4功能覆盖与限制矩阵-20261006.md)。
