# 桂子问津项目最终功能清单与一周实施计划

更新时间：2026-10-05  
计划版本：V1 一周冲刺方案  
当前分支：`v1/20261005-phase1-foundation`

## 1. 文档目的

本文档是项目的总工作分解基线，回答四个问题：

1. 桂子问津最终需要具备哪些功能；
2. 每项功能由哪些模块完成；
3. 当前已经完成到什么程度；
4. 接下来一周按什么顺序开发、如何验收。

“最终功能”表示项目完整目标，“一周交付”表示先做出一条可运行、可验证、可回放的主链。一周结束时，未达到验收标准的阶段必须保留为“未完成”，不能因为有接口、原型或设计文档就标记为完成。

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| 已完成 | 代码、测试或文档已经达到该项当前验收标准。 |
| 部分完成 | 有代码、接口或原型，但缺少生产闭环、测试、治理或集成。 |
| 未完成 | 只有设计、预留接口或待开发任务。 |
| 暂不启动 | 已明确属于后续版本，当前阶段不得实现。 |

## 3. 最终产品目标

桂子问津最终是一个以自我调节学习为核心的长期教育伴生平台。它必须形成以下闭环：

```text
学习者设定目标
  -> 桂子问津诊断知识与学习状态
  -> 学习者作答、探究、讲解和修订
  -> Verifier 生成可追溯证据
  -> 掌握度与保持度更新
  -> 生成复习任务和学习路径建议
  -> Trigger 判断是否介入
  -> Policy 选择教学动作
  -> ActionGovernor 执行规则裁决
  -> Agent/API/Web 向学习者交付
  -> 新交互再次进入证据链
```

系统最终优化三项北极星指标：

- 无辅助表现增量；
- 认知层级跃迁；
- 学习者自主性增益。

## 5. 一周五阶段工作拆分

### 阶段一：1A 学习核心闭环（第 1-2 天）

**状态：未完成。**

**目标：** 把一次 Verifier 判定变成可验证、可重放、可审计的学习状态变化。

**实施任务：**

1. 先新增 Adapter Test，不先复制 DeepTutor 代码。
2. 定义 `LearningEvidence`、`MasteryState`、`RetentionState`、`LearningStateTransition` 和 `ReviewTask` Schema。
3. 实现 `platform/app/learning/mastery_port.py`：
   - `passed -> correct`；
   - `failed -> incorrect`；
   - `partial -> partial`，第一版不更新二值 BKT；
   - `unverifiable` 只入审计。
4. 实现 `platform/app/learning/gates.py`：证据数量、置信度、掌握概率和 qualitative/hybrid gate。
5. 实现 `platform/app/learning/review_port.py`：稳定性、可提取度、遗忘风险、lapse 和 next review。
6. 为 Evidence 消费增加 `evidence_id` 幂等保护。
7. 固定 BKT 与保持度模型的算法版本、参数集 ID 和 replay 规则。

**交付物：**

- 三个 Learning 端口模块；
- 至少 12 类单元测试和 1 条黄金路径集成测试；
- 一条“失败 → 提示 → 通过 → 掌握 → 安排复习”的可回放样例；
- `LearningStateTransition` 事件示例。

**验收标准：**

- 新增测试全部通过；
- 旧有 R-01 至 R-10 和 61 项基线测试不回归；
- 同一 Evidence 重放结果一致；
- 重复 `evidence_id` 只产生一次状态变化；
- `unverifiable` 和 `partial` 不污染第一版长期二值状态。

### 阶段二：1B 决策集成与长期状态骨架（第 3 天）

**状态：未完成。**

**目标：** 让掌握度和保持度真正影响“学什么、何时介入、如何介入”。

**实施任务：**

1. 将 `MasteryState` 和 `RetentionState` 接入 `PathRecommendation`。
2. 第一版只实现三种决策：
   - 掌握度低：`LEARN` 或 `REMEDIATE`；
   - 掌握度高但遗忘风险高：`REVIEW`；
   - 掌握度高且遗忘风险低：`ADVANCE`。
3. 加入 prerequisite 检查，形成最小路径图。
4. 明确 `PathRecommendation`、`TriggerEngine`、`Policy`、`ActionGovernor` 的接口边界。
5. 建立 L1 InteractionEvent 的最小字段：learner、session、KC、evidence、verdict、model、policy、state versions、consent。
6. 为状态变更增加 prior/new 版本与事件序列号，固定相同时间戳下的重放顺序。

**交付物：**

- PathRecommendation v2；
- 三种路径决策及其解释文本；
- L1 事件 Schema 和 replay runner 初版；
- 1B 集成测试。

**验收标准：**

- 给定同一学习者和 Evidence 集合，路径结果确定且可解释；
- 推荐只能产生 `proposed`，不能直接修改学习计划；
- 每次路径决策可追溯到 Evidence 和状态版本；
- Trigger、Policy 和 Governor 能分别测试。

### 阶段三：1C Agent、API 与工作台交付（第 4 天）

**状态：未完成。**

**目标：** 把阶段一和阶段二的结果接回现有 Agent、网关和 Web 工作台，完成最小可用纵向切片。

**实施任务：**

1. Agent Runtime 读取 Learner Model，不在 Runtime 内私有保存学习状态。
2. 将 Verifier → Evidence → State Transition 接入一次真实会话。
3. 增加复习队列 API 和路径推荐 API 的真实数据源。
4. 在计划页展示推荐原因、来源证据和 Diff；采纳、修改、拒绝均留事件。
5. 在陪学页显示当前提示等级、支架类型、复习原因和规则解释。
6. 在成长证据页展示掌握轨迹、遗忘风险和证据钻取入口。
7. 保留 FakeLLM 回退和人工出口，确保模型不可用时学习事件不丢失。

**交付物：**

- 一条从作答到 Web 复习推荐的端到端流程；
- API Schema、错误处理和权限检查；
- 计划、陪学、证据三视图的最小真实数据接入；
- 端到端测试和演示脚本。

**验收标准：**

- 学习者完成一次作答后，页面能看到证据、掌握状态和复习任务；
- 推荐采纳必须经过计划 Diff 和学习者签署；
- 所有动作仍经过 ActionGovernor；
- 页面显示的高层判断可以钻取到原始事件。

### 阶段四：外部能力、派生角色与知识入口（第 5-6 天）

**状态：未完成。**

**目标：** 在主链稳定后接入可替换的外部能力，完成 DeepTutor 裁剪边界内的最小版本。

**实施任务：**

1. 依据 [ADR-002](../决策/ADR-002-DeepTutor裁剪基线-20261005.md) 只抽取 Learning 相关纯逻辑和测试参考。
2. 保留桂子问津的 Schema、Storage、Governor 和事件协议，不复制 DeepTutor Runtime。
3. 提供 Provider Registry 端口，至少支持当前 OpenAI-compatible 客户端、FakeLLM 和一个可配置外部 Provider。
4. 建立最小 RAG：Markdown/PDF 解析、切块、BM25 或向量检索二选一、原文引用和 KC 绑定接口。
5. 实现派生角色最小集：提示者、怀疑者、评审者；所有派生动作走相同 Governor。
6. 建立 `vendor/` 或等价隔离规则、许可证清单和来源记录。
7. 把外部能力适配测试加入回归集。

**交付物：**

- DeepTutor Learning 适配器或等价自建实现；
- Provider Registry 初版；
- 最小知识检索接口；
- 三种派生角色模板及生命周期报告；
- 第三方许可证和来源清单。

**验收标准：**

- 上层模块不直接依赖具体模型厂商；
- 检索结果不能绕过 Verifier 和 KC/KG 接地；
- 派生角色没有越过 Governor 的权限；
- 外部源码、版本、许可证和本地修改可追溯。

### 阶段五：治理、回归、发布与剩余缺口归档（第 7 天）

**状态：未完成。**

**目标：** 形成可交付、可回滚、可继续开发的 V1 检查点。

**实施任务：**

1. 建立首版 30 个冻结回归场景，覆盖 R-01 至 R-10、三类支架、黄金路径和异常路径。
2. 建立红队越界测试：诱导给答案、绕过计划签署、伪造 Evidence、隐私越界、考试模式越权。
3. 校验所有事件包含 learner、KC、Evidence、模型版本、策略版本和状态前后版本。
4. 完成 SQLite replay 验证，记录 PostgreSQL 迁移剩余差异。
5. 完成 Web 关键流程的可用性、权限和无障碍检查。
6. 更新开发状态、阶段日志、测试说明和未完成清单。
7. 生成最终 V1 检查报告，明确“已完成、部分完成、未完成、暂不启动”。
8. 形成一个小而清晰的提交序列，并在确认后推送当前 V1 分支。

**交付物：**

- 30 场景冻结回归集；
- 红队测试报告；
- V1 验收报告；
- 更新后的进度、日志和变更记录；
- 可继续开发的干净 Git 检查点。

**验收标准：**

- 核心测试、集成测试、回归测试和红队测试结果有记录；
- 失败项有明确负责人、依赖和下一步，不被隐藏；
- 可从任意关键结论回放到原始 Evidence；
- 未满足治理条件时，RSI 自动进化保持关闭。

## 6. 一周执行日历

## 7. 依赖关系与执行纪律

```text
Verifier
  -> LearningEvidence
  -> MasteryState / RetentionState
  -> PathRecommendation
  -> Trigger / Policy
  -> ActionGovernor
  -> Agent / API / Web
  -> 回写 InteractionEvent
```

执行时遵守以下顺序：

1. 先写测试，再写适配器，再接外部源码；
2. 先完成 1A，再做 1B，不能用 Web 原型替代核心状态验收；
3. 事实事件先落库，摘要和画像只能作为派生状态；
4. 所有推荐先是 proposed，必须经过学习者确认；
5. 所有 LLM 输出、工具请求和派生角色动作必须过 ActionGovernor；
6. 每天结束更新本文件的阶段状态和日志；
7. 发现阶段超时，保留已经通过的边界，把未完成内容降级为接口和明确缺口，不跨层堆临时代码。

## 8. 一周结束时的明确边界

一周交付的目标是：Learning 核心、决策集成和一条 Agent/API/Web 纵向主链可运行、可验证、可回放，并为 DeepTutor、Memory、RAG、Provider、治理和后续进化保留稳定端口。

以下内容即使已有设计，也必须继续标记为“未完成”或“暂不启动”，直到达到各自验收标准：

- 完整三层 Memory 巩固器；
- PostgreSQL 生产迁移；
- 30 场景冻结回归集和红队套件；
- 完整教师驾驶舱、家长端和金标流程；
- 全量 RAG、知识图谱和多 Provider 生产接入；
- 数字孪生校准、自动 EvolutionJob、自动技能结晶、DSPy 和 LoRA。
