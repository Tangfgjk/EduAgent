# 1. 最终结论

V3 **总体符合桂子问津最初确定的方向，而且核心教育闭环已经真正落地**。

项目已经不再只是“教育聊天机器人原型”，而是具备以下基本形态：

```text
目标与计划
    ↓
学习任务
    ↓
学生行为 / 作答
    ↓
Verifier
    ↓
LearningEvidence
    ↓
Mastery / Retention / Gate
    ↓
PathRecommendation
    ↓
Trigger / Policy
    ↓
ActionGovernor
    ↓
适应性教学动作
    ↓
新的学习行为与证据
```

V3 又在 V2 基础上补上了：

```text
Synthetic Learner
课程准入
测量准入
Simulation Lab
学校隔离 API
学习域 PostgreSQL Repository
CI
隐私与来源治理
耐久作业
备份恢复
```

因此，从**本地研究原型 / 软件 MVP**角度，桂子问津已经进入“可初步使用”的阶段。

但必须区分不同层次的“可用”：

| 使用场景 | 当前判断 |
|---|---|
| 本地开发、功能演示 | **可以使用** |
| 合成学习者仿真与策略筛选 | **可以使用** |
| 研究人员做离线实验 | **可以使用** |
| 单学习者本地学习体验 | **可以初步使用** |
| 教师审核真实课程 | **可以作为工具使用，但流程仍需人工** |
| 少量真人 Pilot | **技术上接近可准备，正式开始前仍需课程、伦理、授权等外部准入** |
| 学校正式部署 | **暂不可** |
| 多租户生产平台 | **暂不可** |
| 宣称提升真实学习效果 | **绝对不可，目前没有真人效度证据** |
| 自动 RSI 自我进化 | **仍应保持关闭** |

最重要的判断是：

> **V3 已经基本完成“我们想做一个什么样的系统”的软件骨架；下一阶段真正缺的不是再加大量功能，而是把现有能力产品化、生产化和实证化。**

# 4. 按最终目标评估当前完成度

以下百分比是基于“最初最终产品愿景”的审计估计，不是项目统计口径或科学测量。

| 领域 | 当前估计 | 评价 |
|---|---:|---|
| 教育规则 / Governor | 95% | 核心结构成熟 |
| Learning Evidence / KT / Retention | 90% | 软件基线较完整，真实校准不足 |
| SRL / 计划 / 路径 / 脚手架 | 85% | 主闭环可跑 |
| Synthetic Validation | 90% | V3 已较完整 |
| 长期 Memory | 60% | 有可追溯骨架，尚非完整画像 |
| RAG / Provider | 55% | 本地最小实现，真实语义与远程模型不足 |
| 学生产品体验 | 65% | 功能很多，但交互仍偏工程工作台 |
| 教师 / 家长 / 学校 | 50% | API 和隔离有基础，完整产品缺失 |
| 生产基础设施 | 50% | 学习域 PG 切片、CI、备份有了，但完整生产栈未完成 |
| 真实教育效度 | 10% | 暂无足够真人证据 |
| RSI 自动进化 | 20% | 基础轨道有，但按设计正确保持关闭 |

综合来看：

```text
本地研究/工程 MVP：约 85%～90%
可控小规模研究 Pilot 技术准备：约 65%
生产级学校平台：约 45%～50%
最终完整愿景：约 65%～70%
```

这里“最终完整愿景只有约 65%～70%”并不是因为代码做得少，而是因为最终目标包含：

- 真人长期效果；
- 真实课程；
- 多用户生产部署；
- 正式教师/家长体系；
- 长期画像；
- 真正的 RSI。

这些不能靠增加代码行数补齐。

# 6. Synthetic Learner 当前效果怎么样

V3 仿真已经不仅是“能跑”，而且有批量实验。

最终记录：

```text
6 profiles
× 5 scenarios
× 2 seeds
= 60 runs
```

结果：

```text
57 completed
3 stopped（模拟学习者主动退出）
0 failed
0 unsupported
0 timed_out
```

同时形成：

- 12 组 baseline / fading 配对；
- seed / item 双留出；
- Brier；
- 独立首次作答表现；
- hint dependency；
- simulation pre-calibration。

但结果也非常值得注意：

> **当前 fading policy 没有显示出明显优势，平均差为 0。**

这不是坏事。

相反，这说明系统没有因为“我们相信脚手架渐撤有效”，就把 Simulator 调成必然证明它有效。

因此当前 Simulation 的正确定位应该继续是：

```text
开发验证
策略筛选
预校准
压力测试
假设生成
```

而不是：

```text
真实学习效果证明
```

# 9. 一个目前仍存在的技术细节问题：Trigger 时钟

当前 `TriggerEngine` 仍使用：

```python
now = now or datetime.now()
```

并且 cooldown 保存在进程内 `_last_fired`。

这对本地原型够用，但对：

- replay；
- 多 worker；
- 多实例；
- 时区；
- 恢复；

不够理想。

建议最终改为：

```text
ClockPort
PersistentTriggerState
```

所有核心时间全部使用 timezone-aware time。

真正的问题反而是：

> **功能过密、开发者味道偏重、学生认知负担较大。**

---

## 10.2 当前学生页面最需要修改的结构问题

### 问题一：学生页混入教师功能

当前 `授权` 页面里直接存在：

- 教师凭据；
- Evidence ID；
- 教师复核；
- Rubric 评审；
- Recovery queue。

即使后端有 token 权限控制，这在产品体验上也不合理。

最终应拆成：

```text
Student App
Teacher App
Parent App
Admin / Research App
Simulation Lab
```

学生页面不要显示教师管理控件。

---

### 问题二：学生页暴露太多内部技术概念

目前 UI 中可以看到或要求输入：

- Evidence ID；
- Session ID；
- Rubric；
- policy 来源；
- source ref；
- recovery job。

这些适合调试工具，不适合最终学生产品。

建议学生侧改为：

```text
我的一次作答
我的复习记录
这条建议为什么出现
查看证据来源
```

内部 ID 放在折叠“技术详情”。

---

### 问题三：“知识与协作”职责过多

当前一个 Tab 同时包含：

- RAG 检索；
- 本地知识导入；
- 策略卡；
- 派生角色；
- 圆桌；
- 教虚拟学生。

最终产品建议拆分：

```text
学习辅助
探究/圆桌
可教智能体
```

“知识导入”更适合教师/admin。

---

## 10.3 推荐最终学生信息架构


## 10.6 前端技术债务

目前：

```text
learning.html ≈ 66KB
index.html ≈ 65KB
```

大量：

```text
HTML + CSS + JavaScript
```

在单文件内。

短期零构建原型很方便，但如果进入最终产品阶段，维护成本会快速上升。

至少应拆成：

```text
web/
  css/
    tokens.css
    layout.css
    components.css

  js/
    api.js
    auth.js
    study.js
    plan.js
    evidence.js
    collaboration.js

  pages/
    student.html
    teacher.html
    parent.html
    simulation.html
```

如果团队后续确定长期做 Web 产品，再考虑 React / Vue / Svelte + TypeScript。

现在不建议为了“现代化”盲目重写前端；先完成职责拆分，再决定框架。
